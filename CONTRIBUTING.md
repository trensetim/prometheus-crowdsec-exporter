# Project structure

- `/src/build` contains all build scripts and the production Dockerfile
- `/src/test/compose` contains everything one needs for local development and testing
- `/src/main/python` contains the actual application code
- `/src/main/helm` contains the production helm chart

# Local development
The `src/test/compose` directory contains a complete local stack with a mock CrowdSec LAPI, Prometheus, and Grafana.

## Start the dev stack
```bash
cd src/test/compose
docker compose up --build
```

| URL                                | Service                              |
| ---------------------------------- | ------------------------------------ |
| http://localhost:3000              | Grafana (`admin` / `dev-grafana-pw`) |
| http://localhost:9090              | Prometheus                           |
| http://localhost:8000/metrics      | Exporter metrics (direct)            |
| http://localhost:8080/v1/decisions | Mock CrowdSec LAPI                   |

## Development workflow
```bash
# ... Always first cd here
cd src/test/compose

# Code changed (src/) → restart only, no rebuild needed
docker compose restart exporter

# requirements.txt changed → rebuild
docker compose up --build exporter

# View live logs
docker compose logs -f exporter

# Manual LAPI test
curl -H "X-Api-Key: dev-bouncer-key-12345" http://localhost:8080/v1/decisions | jq .

# Check metrics
curl -s http://localhost:8000/metrics | grep crowdsec

# Tear down and clean volumes
docker compose down -v
```

# Build
## Production image (distroless)
```bash
docker build \
  --build-arg APP_VERSION=1.0.0 \
  --build-arg GIT_COMMIT=$(git rev-parse --short HEAD) \
  -f src/build/docker/Dockerfile \
  -t crowdsec-exporter:1.0.0 \
  .
```

The production image uses `gcr.io/distroless/python3-debian12:nonroot`:
- No shell, no package manager → minimal attack surface
- Runs as uid 65532 (nonroot) → satisfies `runAsNonRoot: true`
- Multi-stage build → only application code and locked dependencies in final image

## Using custom OpenSSL Trust Stores during build

If you are running behind a MITM Proxy that necessitates including it's custom CA certificate in your trust store,
you will also need to mount that (readily-compiled) trust store inside the containers you use (eg. during build).

In such cases, adjust the `Dockerfile` temporarily on your host, but do not commit such changes. \
The build process in CI must stay clean.

```bash
# in bash
docker build --secret id=host_openssl_cacerts,src=/etc/ssl/certs/ca-certificates
```

```Dockerfile
# in Dockerfile
RUN --mount=type=secret,id=host_openssl_cacerts,target=/etc/ssl/certs/ca-certificates.crt # \
    # pip install ...
```

```yaml
# in compose.yaml
secrets:
  host_openssl_cacerts:
    file: /etc/ssl/certs/ca-certificates.crt
services:
  foobar:
    build:
      secrets:
        - host_openssl_cacerts
```

To accelerate that process, you may find this one-liner helpful:

```bash
git apply <src/test/host_openssl_cacerts.patch
```

## Prerequisites
- Docker with BuildKit enabled (`export DOCKER_BUILDKIT=1` or set in `/etc/docker/daemon.json`)

# Dependency management
Direct dependencies are listed in `src/main/python/requirements.in`. Locked, hashed versions are in `src/main/python/requirements.txt` (generated by `pip-compile`).

```bash
cd src/main/python/ ; pip-compile --generate-hashes requirements.in
```
